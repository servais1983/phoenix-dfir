## [Unreleased]

### Added

- `phoenix eval --record FILE` writes every answer of the local model to a
  JSON Lines file and `--replay FILE` runs the same investigation with no
  model (`llm_record.py`): the tools, the verifier and the gates run for real,
  and a call the recording does not hold stops with an error.
- SigmaHQ rules on Entra ID sign-in and audit logs, Microsoft 365 audit and
  GCP audit logs: `scan_records` takes several services and a table of the
  rule field names an export spells differently (`status.errorCode` for
  `ResultType`, `protoPayload.methodName` for `gcp.audit.method_name`...).
  The bundled subset grows to 70 rules (14 Entra ID, 6 GCP, 3 Microsoft 365).

### Fixed

- No silent cap any more: `parse_log_file`, `parse_csv`, `parse_json_file` and
  `parse_evtx` returned the first 500 events and stopped at 1000 to 10000
  records without saying so (an SSH brute force after line 500 was missed).
  They read up to `PHOENIX_PARSE_MAX_RECORDS` (500000), give every event to
  the detectors and the evidence index, send the LLM a 500 event preview and
  report `truncated` with a warning. The evidence index cap
  (`PHOENIX_INDEX_MAX_EVENTS`, 1000000) and the entity graph cap
  (`graph_build` returns `events`) are reported too.

## [4.16.0] - 2026-10-30

Phase 4: benign counter-examples, robust detections, Sigma beyond Windows,
full scans of large files.

### Added

- Benign counter-examples (`eval/build_benign_cases.py`): one benign case per
  deterministic detector (SSH typos, backup renames, NTP and presence polling,
  a truncated Kerberos log, an administrator download). The suite has 25 cases.
- SigmaHQ rules on cloud and Linux records: `sigma_engine.scan_records` runs
  the AWS CloudTrail rules in `cloud_parse_log` and the Linux auditd rules in
  `linux_parse_auditd` on the raw records (nested fields as dotted names), each
  alert citing the row or the line of its event. The bundled subset grows to
  47 rules (12 CloudTrail, 10 auditd).

- Shell history exfiltration chain (`logdetect.history_alerts`): an archive
  created (T1560.001), uploaded to an external address (T1048) and deleted with
  what it holds (T1070.004); a sixth benign case archives to the internal NAS.
- Verified findings timeline (`verifier.verified_timeline`,
  `metrics.verified_timeline`) shown in the AI Investigator page with technique
  and artifact filters.
- Volume test: 100 000 Windows events generated by `eval/build_volume_events.py`
  are scanned to the end in about 4 s and 240 MB.

### Fixed

- `sigma_scan` read only the first 1 000 events of a JSON export and the first
  2 000 of an EVTX, silently. It now reads every event up to
  `PHOENIX_SIGMA_MAX_EVENTS` (default 1 000 000), reports `events_scanned` and
  `truncated`, and warns when the end of a file was not scanned. JSON Lines
  exports are read too.
- The deterministic evaluation kept the files extracted from a disk image
  outside the case, so their findings could not be verified.

### Changed

- The deterministic evaluation job installs The Sleuth Kit: with it, the
  verified recall without LLM is 100 % on the 26 cases.
- Flow beaconing leaves out periodic infrastructure protocols (NTP, DNS, DHCP,
  NetBIOS, mDNS, SNMP).
- The download cradle rule keeps the Net.WebClient pattern only
  (Invoke-WebRequest and Start-BitsTransfer are routine in administration).
- A service ticket without TGT is called forged only when the log covers a TGT
  lifetime before it, or when it is RC4 while every TGT of the log is AES;
  otherwise a low, inconclusive alert without technique is raised.

## [4.15.0] - 2026-10-30

Phase 2: verified findings only, real Sigma engine, agent contracts.
Phase 3: deterministic detections that raise the verified ATT&CK recall of the
LLM-free evaluation from 71 % to 97 %, and the verification in the console.

### Added

- Text log detections (`logdetect.py`) in `parse_log_file`: SSH brute force
  from one address (T1110) and the successful login that follows (T1078);
  Windows events written as `EventID=<id> Key=Value` lines go through the
  built-in and pySigma rules, each alert citing its line.
- Flow export beaconing (`flowdetect.py`) in `parse_csv`: regular connections
  with near constant volumes to an external address, on the thresholds of the
  packet capture detection, citing every row.
- File export detections (`filedetect.py`) in `parse_csv`: mass encryption by
  appended extension (T1486) and MFT timestomping when the SI creation time is
  earlier than the FN one (T1070.006).
- Kerberos correlation (`kerberos.py`) in `sigma_scan`: a service ticket
  request without any TGT request of its account, in a log that has TGT
  requests, is reported as a forged ticket (T1558.001).
- `deobfuscate_artifact` is offered for exports (CSV, JSON, logs) that hold an
  encoded command and reports every decoded payload with behaviour indicators
  as an alert with their techniques (T1027, T1105, T1562.001, T1620...).
- A 30th built-in rule: PowerShell download cradle in a script block (4104,
  T1105), also exported as Sigma YAML.
- Investigator console: the AI Investigator page shows the citation coverage
  of the report, the unlinked sentences and why, and the tokens and tool
  calls per agent. `metrics.citations.unlinked` carries those sentences.

- Deterministic verifier (`phoenix_dfir_mcp/verifier.py`). A finding is
  `verified` only when it cites a reference (`record_id`, `row`, `line`, `pid`,
  `inode`) that a tool produced for that artifact and every entity it names
  (IP addresses, domains, hashes, e-mail addresses, URLs) appears in the
  referenced events. A shield detection is verified by replaying the shield on
  its artifact. No LLM is involved: the same case gives the same verdicts.
- Report citations: every factual sentence of a report (IoC, ATT&CK technique,
  timestamp or evidence reference) must end with `[F<id>]` of a verified
  finding. `save_report` returns `verification`, `citations` and
  `unlinked_sentences`; the report annex states the coverage; the loop metrics
  expose `citations`.
- Sigma engine on pySigma and its SQLite backend (`sigma_engine.py`). The
  events of an artifact go into an in-memory SQLite table (read only while the
  rules run) and every match keeps the `record_id` or `row` of its event.
  `sigma_scan` runs it next to the 29 built-in rules and returns `engines`
  with the rules and alerts of each engine; alerts carry `engine`, and the
  SigmaHQ ones `rule_author` and `rule_url`.
- A subset of 25 SigmaHQ rules (release `r2026-07-01`, Detection Rule License
  1.1, `data/sigma/sigmahq/NOTICE.md`) ships with the package.
- `phoenix rules [list|sync|import|export-builtin]`: rule folders and usable
  rules, download of the pinned SigmaHQ release into the data folder (with an
  optional SHA-256 check, `PHOENIX_SIGMAHQ_SHA256`), import of a zip of rules
  (rule files only, never outside the store), and the built-in rules as Sigma
  YAML (`data/sigma/phoenix`, same alerts as the built-in engine on the
  evaluation suite).
- `PHOENIX_SIGMA_RULES` adds rule folders. The `rules_path` of the Sigma
  connector is now loaded, and its connection test counts the rules pySigma
  can run.
- `phoenix doctor` reports the Sigma engine. EVTX events now carry their
  `channel`.
- Agent contracts (`contracts.py`): Pydantic v2 models for evidence
  references, findings, hypotheses, verdicts, phase outputs and the
  quarantined extraction, exported as JSON Schema (`phoenix schemas`).
  `ask_json` asks for a structured answer at temperature 0 with the contract
  as response format and at most 2 new attempts told the validation errors;
  token usage is logged per agent.
- Specialized agents (`agents.py`, `phoenix agents`): orchestrator, triage and
  collection, logs, memory, disk and timeline, network, cloud and identity,
  IoC enrichment, ATT&CK, verifier and writer, each with a model role, a tool
  allowlist, a token budget (`PHOENIX_AGENT_MAX_TOKENS`) and its contract.
- `phoenix eval` scores the four phase 2 criteria (`summary.criteria`):
  ATT&CK recall over verified findings >= 0.8, no forbidden technique on a
  benign case, injection detected, 100 % of factual report sentences linked
  to a verified finding. `--criteria` and `--require <criterion>` gate them.
  `--deterministic` scores them without any LLM (indexed triage, verified
  findings, deterministic report); CI gates the four criteria in this mode
  on the whole suite.
- Bounded parallel extraction in the deterministic triage
  (`PHOENIX_EXTRACTION_WORKERS`, `phoenix triage --workers`): the report is
  byte-identical whatever the number of workers.

### Changed

- Kerberoasting alerts on service tickets without TGT are reclassified as a
  forged ticket: the golden ticket case no longer reports T1558.003.
- The beaconing detection of a capture indexes the SNI, JA3 and JA4 it states,
  so a finding citing its row verifies on them.
- A citation links a report sentence only when the entities it states appear
  in the events of the cited findings (report gate, annex, evaluation).
  Report metadata written by Phoenix (save_report header, annex head) is not
  counted as a factual sentence.

- The correlation and counter analysis gates run the verifier first; a
  critical or high finding that is not verified blocks the correlation gate
  with the deterministic reason. The report gate rejects factual sentences
  without a citation of a verified finding.
- The final verification status of a finding is the deterministic one. The
  independent LLM verification can still refute a finding, never verify it.
- Each phase is led by an agent and offers only the tools of its team (the
  tool lists are unchanged). `metrics.phases` rows follow the `phase_output`
  contract (new keys `agent`, `findings`, `tokens`) and `metrics.agents` gives
  the tokens of each lead agent and the tool calls of each specialist.
- `record_finding` and `add_hypothesis` reject arguments off their contract
  with the exact errors. The quarantined extractor retries an unusable answer
  at most twice (`contract_retries`, per agent usage in `dual_llm.agents`).
- `pydantic>=2.5` is a core dependency.
- `toolkit.py` keeps the registry, the evidence index, `run_tool` and the
  extensions; the core tools moved to `tools_artifacts`, `tools_external`,
  `tools_case`, `tools_disk` and `tools_evidence`. The MCP tool list, names,
  descriptions, schemas and order are unchanged and every name is still
  reachable as `toolkit.<name>`. Code that monkeypatches a core tool helper
  must now patch it in its family module.
- The `sigma` extra installs pySigma and pysigma-backend-sqlite on Python
  3.11+ (pySigma 2 requirement). Without them only the built-in rules run and `sigma_scan` reports pySigma as not
  available.
- `render_markdown` lists verified findings and, separately, the excluded
  non verified findings with their reason. The fallback report written when
  the LLM gives none only contains verified findings, each cited.

### Fixed

- The guidance of `cloud_hunt` and `macos_hunt` read as a tool call to the
  anti-injection shield, which flagged an injection on benign cloud, identity
  and macOS cases.

## [4.14.0] - 2026-10-30

Phase 1: local first, every OS, evidence integrity, deterministic mode.

### Added

- Installable package `phoenix-dfir` (`pyproject.toml`) with the `phoenix`
  command line and the extras `web`, `memory`, `sigma`, `yara`, `disk`, `evtx`,
  `analytics`, `intel` and `all`. The version is single-sourced from
  `phoenix_dfir_mcp.__version__` (backend health, MCP server info,
  `package.json`).
- `phoenix triage <case>`: deterministic triage with no LLM. It keeps only the
  detections the tools emitted with an observed reference, never writes into
  the case and returns byte-identical JSON across runs. Files extracted from a
  disk image are triaged in a second pass.
- Standard case layout (`evidence/`, `derived/`, `reports/`, `custody/`) with
  `manifest.sha256`: `phoenix ingest` copies, hashes and makes the evidence
  read-only; `phoenix verify` re-hashes it and reports modified, missing and
  unlisted files. Ingestion, verification, triage runs and cloud LLM consents
  are sealed in the custody ledger.
- llama.cpp provider (`PHOENIX_LLAMACPP_URL`, `PHOENIX_LLAMACPP_MODEL`) and
  `PHOENIX_LLM_SEED`.
- LM Studio (`lmstudio`, `http://localhost:1234/v1`) and Jan (`jan`,
  `http://localhost:1337/v1`, optional `PHOENIX_JAN_API_KEY`) local providers.
  `auto` also tries them after Ollama and llama.cpp.
- Role based model selection (`investigator`, `reviewer`, `extractor`,
  `analyst`): every LLM driven process (five-phase and loop engines,
  verification, adviser review, dual-LLM extraction, console file analysis)
  asks for its role, and the best model the local server lists is ranked
  deterministically from its name (family, size up to
  `PHOENIX_LLM_MAX_PARAMS_B`, kind). `PHOENIX_LLM_MODEL_<ROLE>` and the provider
  model variables still win. `phoenix models [--check]`, `GET /api/llm/models`,
  the role list in `phoenix doctor` and on the AI Investigator page.
- External tool adapters for Volatility 3, Hayabusa, The Sleuth Kit, EZ Tools
  and TShark (`detect`, `version`, `capabilities`, `run`), with
  `PHOENIX_<TOOL>_CMD` overrides.
- `phoenix doctor` (text and JSON): LLM provider and reachability, external
  tools with versions or fallbacks, optional modules, sandbox, path policy and
  storage locations.
- `phoenix web`: the investigator console served by waitress on Windows, macOS
  and Linux, listening on 127.0.0.1 by default.
- CI on Ubuntu, Windows and macOS (Python 3.10 and 3.12), `pipx install` job,
  deterministic evaluation job, ruff; `eval/triage_acceptance.py`.
- `CLAUDE.md` with the project conventions.

### Changed

- **LLM default**: the provider defaults to `ollama` (was `github`). `auto`
  only picks a reachable local server (Ollama, then llama.cpp) and never a
  cloud provider. `openai` and `github` are refused unless
  `PHOENIX_ALLOW_CLOUD_LLM=1`; a local provider pointed at a public host is
  refused the same way. Calls use temperature 0, a fixed seed and at most two
  retries on transient errors.
- REST: `GET /api/autonomous/status` reports `copilot_configured: false` for a
  cloud provider without the opt-in, and `POST /api/autonomous/investigate`
  explains the local default and the opt-in in its 400 error.
- REST: `POST /api/analyze` falls back to the native parsers, with an explicit
  note, when the legacy LLM analysis gets no answer. The legacy analysis now
  goes through the local-first client.
- MCP: `phoenix serve-mcp` (alias `serve`) starts in strict mode and denies
  every file access until `PHOENIX_TOOL_ROOTS` is set. `.vscode/mcp.json`
  allows `cases/`.
- MCP: `ground_truth.json` is never listed as a case artifact; on a case with
  the standard layout, `reports/`, `custody/` and `manifest.sha256` are not
  artifacts and derived files are written to `derived/`.
- MCP: the server info version is now the package version (was `1.1.0`).
- `phoenix investigate` runs the deterministic triage, with a message, when no
  LLM answers (`--no-triage-fallback` keeps the error).
- Path checks use `realpath`, `normcase` and `commonpath` everywhere: case
  insensitive on Windows, different drives never match, UNC paths handled.
- Data locations: an installed package keeps its database, vault, uploads,
  reports, sessions, inbox and development secret key in the per-user data
  folder of the OS (`platformdirs`, `PHOENIX_DATA_DIR`); a source checkout and
  the Docker image keep `backend/`. The vault no longer probes `/mnt/evidence`
  (the image sets `PHOENIX_EVIDENCE_VAULT`).
- Dependencies: `platformdirs`, `defusedxml` and `waitress` added; gunicorn is
  no longer installed on Windows. bandit and pip-audit now block the CI.

### Security

- The legacy CSV handler no longer runs LLM-generated code with `exec()`;
  evidence column names could steer that code.
- Evidence XML (EVTX records) is parsed with DTDs and entities refused.
- Evidence sent to the LLM by the legacy analysis goes through the
  anti-injection shield; VirusTotal is only called when `API_KEY_VT` is set.
- On Windows, the development secret key warns that only NTFS ACLs restrict
  it instead of silently ignoring `chmod`.

## [4.11.0] - 2026-10-15

### Security

- **Path traversal in `/api/analyze`** (critical): analysis now takes an
  `artifact_id` resolved from the database; a bare upload name is only
  accepted when it resolves inside the uploads folder. The JWT signing key
  could previously be read through this endpoint.
- **Accounts**: self-registration is closed by default. The first admin is
  created from `PHOENIX_ADMIN_USERNAME` / `PHOENIX_ADMIN_PASSWORD` or with a
  one-time setup token printed in the server log; admins manage users and
  roles (admin, analyst, viewer) from Settings.
- **Case-level access control**: investigations have members; every route,
  list and export checks membership (404 when denied). Viewers are read-only.
- **Real-time isolation**: WebSocket events are delivered per investigation
  room; expired or revoked sessions are disconnected; the token is no longer
  accepted in the query string.
- **Sessions**: refresh token in an HttpOnly, SameSite=Strict cookie; access
  token kept in memory; all sessions revoked on password, role or status
  change.
- **Brute force**: the client IP is no longer taken from a spoofable
  `X-Forwarded-For` (set `PHOENIX_TRUSTED_PROXIES` behind a proxy); per-account
  lockout after repeated failures.
- **AI investigator isolation**: tool sandbox, forced case directory and
  evidence index are scoped to each job; the prompt-injection shield handles
  Unicode lookalikes and more phrasings.
- **Hardening**: streamed hashing and disk extraction, size caps on JSON and
  log lines, symlinks rejected in the inbox, unique upload names, CSV formula
  neutralization, IoC validation and URL encoding in connectors, masked
  integration secrets, generic error messages, optional `/metrics` token,
  per-user job quota.
- **Dependencies**: Flask 3.1, Werkzeug 3.1, flask-cors 6, python-socketio 5.17,
  npm packages updated (0 known advisories).

### Fixed

- Production stack: gunicorn pinned below 26, which removed the eventlet worker
  used by `docker-compose.prod.yml`.
- WebSocket transport refused same-origin connections under eventlet (the
  origin check now reads the WSGI environ).
- Uploads from the analyzer page were not attached to the selected case.

## [4.10.0] - 2026-10-15

### Added: Disk images (The Sleuth Kit)

- **`phoenix_dfir_mcp/disk.py` module**: reads disk images **without
  mounting** them (E01/Ex01, dd/raw/img/001, VMDK, VHD/VHDX, AFF) using The
  Sleuth Kit. `.raw`/`.bin` files are classified as disk or memory by
  signature (MBR, GPT, NTFS, ext).
- **Five MCP tools**: `disk_status`, `disk_image_info` (partitions, offsets,
  file system), `disk_list_files` (directory tree, path filter, **deleted
  files**), `disk_timeline` (**MACB** timeline indexed into the FTS5
  super-timeline), `disk_extract_artifacts` (`windows`, `linux` and `auto`
  profiles: EVTX, registry hives, Amcache, Prefetch, scheduled tasks, SRUM,
  NTUSER/UsrClass, LNK, PowerShell history, browser histories, $MFT, Linux
  logs, crontabs, SSH keys, systemd services).
- Extraction to `extracted/<image>/p<offset>/` with a **per-file SHA-256**
  and an `extraction_manifest.json` manifest. Extracted files automatically
  enter the coverage gate of subsequent phases.
- **Inode citations**: new `inode` reference type (including the composite
  `128-128-1` form), validated against the evidence index.
- Console: **Disk images** agent showing actual The Sleuth Kit
  availability. Image extensions are accepted on upload and in the vault.
- The Sleuth Kit is installed in the Docker image and in CI.

### Added: Benchmark with factual answer key

- `ground_truth.json` accepts **facts** (`facts`): question, accepted
  answers, related terms. Two scores: `fact_exact` (exact answer cited in
  the report) and `fact_detection` (topic addressed). A `--min-fact-exact`
  threshold is available for evaluation CI.
- New **`disk_image_data_exfiltration`** case: a reproducible ext4 image
  (`eval/build_disk_case.py`) of a workstation where a confidential folder is
  archived, exfiltrated over HTTP and then deleted; four factual questions.
- End-to-end test: 5/5 quality gates passed and 100% exact facts on this
  case.

### Changed

- Documentation fully rewritten (README, Windows/Docker guide, evaluation
  bench, MCP server).

## [4.9.0] - 2026-10-15

### Added: Five-phase investigation with quality gates

- **Phase engine** (`phoenix_dfir_mcp/phases.py`, default): Inventory,
  Extraction, Correlation, Counter-analysis, Report. Per-phase prompt and
  tool allowlist; **deterministic quality gates** (case memory, evidence
  index, report sections); retry with the exact list of gaps (at most 2),
  then continuation with partial results flagged; compact state passed
  between phases; deterministic fallback report. Each gate is sealed in the
  chain of custody and visible in the console.
- **SQLite FTS5 super-timeline** (`evidence_db.py`): all deterministic tool
  outputs are normalized (UTC timestamp, host, user, process, evidence
  references); new tools `search_evidence`, `get_timeline`, `list_sources`.
  Citation validation also relies on this persistent index (valid across
  restarts).
- **Counter-analysis**: `challenge_finding` (upheld / weakened / dismissed)
  and the `audit_tool_coverage` / `audit_evidence_coverage` audits;
  `declare_no_incident` to close a clean case without inventing findings.
- **`PHOENIX.md` briefing** injected into every phase (`.md` upload
  allowed).
- **Exports**: ATT&CK Navigator layer and IoC CSV, downloadable from the AI
  Investigator page; dismissed findings are excluded.
- Evaluation bench: `--mode phased|loop` to compare the two engines.

## [4.8.0] - 2026-10-15

### Security

- **Authenticated WebSocket**: the client sent no token, and the server
  accepted every connection and broadcast investigation events (investigator
  steps, findings, chain of custody, validation requests) to all clients.
  The access token is now sent on every (re)connection, anonymous or invalid
  connections and connections using a refresh token are rejected, and all
  events are emitted only to the authenticated clients room
  (`extensions.emit_secure`).

### Added

- **Investigator evaluation bench** (`phoenix_dfir_mcp/evaluation.py`,
  `python -m phoenix_dfir_mcp eval`): annotated cases (`ground_truth.json`),
  ATT&CK technique recall, forbidden techniques, IoC recall, evidence
  grounding (findings rejected when they lack an observed reference),
  injection detection, false positives on clean cases, cost; Markdown/JSON
  reports and blocking thresholds. Initial suite of 4 cases in `eval/suite/`.

### Changed

- The "SOC Console" becomes the **DFIR Investigator Console** (page,
  navigation, `GET /api/console/status` API, documentation): Phoenix is a

## [4.7.0] - 2026-10-13

### Added: LLM loop security

  output handed to the LLM (investigator, verification and adviser passes,

## [4.3.1] - 2026-07-09

### Fixed: Production hardening after a full real E2E test (30 checks)

An end-to-end test against a real running backend (auth, uploads, Copilot
loop over HTTP, WebSocket, inbox drop, real Windows EVTX) revealed and fixed
the following:

- **WebSocket never delivered from worker threads**: the eventlet server
  ignored `socketio.emit()` calls from analyses, the investigator and the
  watcher. `eventlet.monkey_patch()` is now applied at the top of `app.py`
  (aligning dev and gunicorn prod). Real-time progress now actually works.
- **Frontend never served in single-container mode**: the Docker image
  copied the build into `/app/frontend` but Flask did not serve it. The
  backend now serves the build (including SPA fallback), so the full
  interface is available at `http://<host>:5000` (`PHOENIX_FRONTEND_DIR`, or
  `dist/` at the root).
- **CORS/WebSocket blocked outside localhost**: origins are configurable via
  `PHOENIX_CORS_ORIGINS` (exposed in both compose stacks), and the server's
  own origin is accepted automatically (team access by IP). Frontend: the
  API/WebSocket URL is auto-detected from the page's origin, and the
  "Backend URL" field in settings now takes effect.
- **More reliable EVTX parsing**: the Rust `evtx` engine (pyevtx-rs,
  prebuilt wheels) is used first, with python-evtx as a fallback. Validated
  on a real Windows Security log (999 events, real Sigma alerts).
  `requirements-optional.txt` can no longer fail as a whole (hexdump
  removed).
- **Protected evidence**: `cleanup_old_files` now only deletes orphaned
  uploads; artifacts attached to an investigation are NEVER purged.

  X-Forwarded-* propagation, /metrics restricted to the internal subnet,
